# 5. Limitations and Mitigation Scenarios

## Platform limits (summary)

Source: [Dataflow quotas](https://cloud.google.com/dataflow/quotas) and [Compute quotas](https://cloud.google.com/compute/quotas) — verify before production.

| Limit | Typical constraint | Impact |
| --- | --- | --- |
| Workers per job | Default quota ~1,000 (region-dependent) | Mega-scale needs quota uplift |
| Persistent disk per worker | Up to 64 TB (machine dependent) | Rarely binding with Streaming Engine |
| Job duration | Streaming: indefinite; batch: practical limits on preemption | Long batch may need checkpoint patterns |
| Side input size | Must fit worker/Broadcast memory model | Large dims need async lookup pattern |
| Hot keys | Single key dominates shuffle | Stragglers, autoscale ineffective |
| Python UDF performance | Slower than Java for CPU-heavy | Use Java/Go for hot paths |
| Cold start | New worker spin-up 1–3 min | Affects sudden scale-out latency |
| Regional service | Dataflow regional | Multi-region = multiple jobs |

## Limitation → scenario → mitigation

| Limitation | Scenario | Mitigation |
| --- | --- | --- |
| Hot-key skew | Top-product enrichment | Salt keys; pre-aggregate; broadcast small dims only |
| High shuffle cost | 10-way join on batch | Filter early; reduce key cardinality; partition input |
| 24/7 streaming cost | Always-on metrics pipeline | At-least-once mode; CUDs; right-size `maxNumWorkers` |
| Duplicate records | At-least-once to BQ | Idempotent merge keys; switch to exactly-once |
| Python GIL CPU bound | JSON parsing 100k/s | Java `ParDo`, Beam SQL, or pre-parse upstream |
| Large side input | Country reference table (small OK) | Use Spanner/BQ lookup transform instead |
| Stateful memory | Huge session state | Shorter session gap; RocksDB equivalent via Streaming Engine |
| Breaking schema change | Add field to Avro | Versioned parser + DLQ; drain job before deploy |
| Vendor lock-in to GCP runner | Multi-cloud mandate | Author in Beam; run on FlinkRunner elsewhere |
| Sub-second latency | Tick analytics | Dataflow not ideal — push compute to consumer or use Flink |

## When not to use Dataflow

| Situation | Better fit |
| --- | --- |
| Simple file copy GCS → BQ | BigQuery load job / transfer service |
| Scheduled SQL only | BigQuery scheduled queries |
| Kafka-native stream SQL | ksqlDB, Flink SQL |
| Interactive ad-hoc | BigQuery, Spark notebook |
| Ultra-low-latency CEP (< 50 ms) | Dedicated Flink cluster |
| Tiny event volume (< 1M/day) | Cloud Functions + Pub/Sub push |

## Anti-patterns

1. **Unbounded side input** — loading 50 GB lookup table as broadcast.
2. **No `maxNumWorkers`** — runaway autoscale bill during incident.
3. **Synchronous external API per element** — use batching/async IO transforms.
4. **Ignoring watermarks** — processing-time windows on out-of-order data.
5. **Disabling Streaming Engine** — higher worker RAM, higher cost.
