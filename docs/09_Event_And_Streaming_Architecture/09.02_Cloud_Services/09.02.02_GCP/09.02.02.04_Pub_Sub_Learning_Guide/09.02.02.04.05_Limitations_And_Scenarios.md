# 5. Limitations and Mitigation Scenarios

## Platform limits (summary)

Source: [Pub/Sub quotas and limits](https://cloud.google.com/pubsub/quotas) — verify current values before production sign-off.

| Limit | Typical value | Impact |
| --- | --- | --- |
| Message size | 10 MB (`data` field) | Large payloads need GCS reference + pointer event |
| Attributes per message | 100 | Keep metadata concise; avoid payload in attributes |
| Publish request size | 10 MB total, 1000 messages | Batch within bounds |
| Topic retention | Up to 31 days | Not a multi-year log; use lake for history |
| Subscriptions per topic | 10,000 | Sufficient for most enterprises |
| Publish throughput (large region) | Up to ~4 GB/min per project quota tier | Request quota increases for mega-scale |
| Ordering | Per ordering key, regional | No global total order |
| Seek / replay | Pull subscriptions | Push subs need alternate replay pattern |

## Limitation → scenario → mitigation

| Limitation | Affected scenario | Mitigation |
| --- | --- | --- |
| No long-term log retention | Multi-year audit, regulatory archive | BigQuery or Cloud Storage export subscription; lake retention |
| Ordering key hotspots | Per-customer strict sequence at mega scale | Shard keys; partition by hash; consider Kafka for extreme hot keys |
| Minimum 1 KB per API request | High-volume tiny events | Aggressive publisher batching; aggregate at edge |
| Push delivery timeouts | Slow HTTP handlers | Ack fast, process async; or switch to pull/Dataflow |
| Cross-region latency + transfer cost | Global user base, single region topic | Regional topics; geo-routed publishers |
| No Kafka wire protocol | Existing Kafka clients/tools | Kafka Connect bridge, Confluent cluster, or import topics |
| Attribute/filter expressiveness | Complex content-based routing | Route in Dataflow or use multiple filtered subscriptions |
| Subscription expiration (31d idle default) | Ephemeral dev sandboxes | Terraform lifecycle; monitoring on subscription activity |
| Exactly-once regional scope | Multi-region active-active | Idempotent sinks + dedup store at boundaries |
| 10 MB message cap | Video/binary payloads | Store in GCS; publish reference event with URI + checksum |

## When not to use Pub/Sub

| Situation | Better fit |
| --- | --- |
| Kafka ecosystem standard across all clouds | MSK, Confluent, self-hosted Kafka |
| Heavy stateful stream SQL at scale | Flink on Dataflow or GKE, or Kafka Streams |
| Sub-millisecond internal IPC | In-process queues, gRPC streaming |
| Request/reply synchronous RPC | gRPC, HTTP APIs |
| Fixed low-cost predictable 24/7 high throughput (legacy) | Pub/Sub Lite was option — **Lite deprecated March 2026**; use standard Pub/Sub with FinOps tuning |

## Risk scenarios

### Poison message loop

**Symptom:** Infinite redelivery of bad payload.  
**Mitigation:** Dead-letter topic after N delivery attempts; alert on DLQ depth; schema validation on publish.

### Push overload

**Symptom:** Cloud Run 503, growing backlog.  
**Mitigation:** Increase max instances, reduce push concurrency, extend ack deadline, or migrate to pull/Dataflow.

### Cost surprise from fan-out

**Symptom:** Bill scales with subscriptions × throughput.  
**Mitigation:** Filter subscriptions; consolidate consumers; model in [Costing](09.02.02.04.06_Costing.md).

### Ordering key hotspot

**Symptom:** Single key throttles pipeline.  
**Mitigation:** Redesign key granularity; split topics; evaluate partition log (Kafka).
