# Event vs Message

## Core distinction

| Dimension | Message | Event |
| --- | --- | --- |
| Intent | Command or request ("do this") | Fact ("this happened") |
| Coupling | Often point-to-point | Many subscribers possible |
| Routing | Queue semantics common | Pub/sub and log semantics |
| Schema | Payload for action | Past-tense domain fact |
| Example | `CreateOrder` command | `OrderCreated` event |

Messages optimize **workflow coordination**; events optimize **decoupled state propagation**.

## Enterprise implications

- **Command-query separation**: Commands via APIs or task queues; domain facts via event log.
- **Event-carried state transfer**: Events carry enough data that consumers avoid synchronous calls.
- **Notification-only events**: Small events that trigger lookups — higher coupling, lower payload cost.

## Anti-patterns

- Using the broker as a RPC bus with request-reply everywhere (latency, coupling).
- Publishing commands on a shared event bus without access control boundaries.
- Treating database change rows as business events without domain semantics.
