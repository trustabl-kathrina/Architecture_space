# Event Time vs. Processing Time

In stream processing, dealing with time is one of the most complex challenges due to network delays, distributed systems, and out-of-order data.

## Time Domains
1.  **Event Time**: The time the event actually occurred at the source (e.g., when a user clicked a button on their phone). This timestamp is embedded in the event payload.
2.  **Ingestion Time**: The time the event arrived at the event broker (e.g., Kafka broker timestamp).
3.  **Processing Time**: The wall-clock time when the event is being processed by the stream processing engine (e.g., Flink, Spark).

## The Challenge: Out-of-Order Events
Because of network latency, device offline states, or distributed partitioning, events may arrive at the processing engine in a different order than they originally occurred. 

### Advanced Concept: Clock Skew
If the source systems generating the "Event Time" do not have perfectly synchronized clocks (via NTP - Network Time Protocol), an event generated at 10:00 AM on Server A might actually have occurred after an event generated at 10:01 AM on Server B. Stream processors cannot solve fundamental source clock skew; they must rely on infrastructure-level NTP sync to ensure Event Time is trustworthy.

## Architectural Solutions
*   **Watermarks**: A heuristic mechanism used in stream processing (like Apache Flink or Google Dataflow) to signal progress in *Event Time*. A watermark of `T` declares that the system expects no more events with an event time `< T`. It allows the system to close and emit time-based windows.
*   **Late Data Handling**: Strategies for dealing with data that arrives *after* the watermark has passed:
    *   **Drop**: Ignore the late data (fastest, but loses data).
    *   **Dead Letter Queue (DLQ)**: Send late data to a side queue for auditing or manual processing.
    *   **Update/Retractions**: Emit an updated result for the window, correcting the previous computation.
