# 2. Architecture of Flyte

## Control plane vs execution plane

| Plane | Responsibility |
| --- | --- |
| **Control plane** | FlyteAdmin, FlytePropeller, Datacatalog, Console |
| **Execution plane** | Task pods on Kubernetes (Spark, Python, containers) |

## Core components

| Component | Function |
| --- | --- |
| **FlyteAdmin** | Project/domain registry, workflow registration, execution API |
| **FlytePropeller** | K8s operator reconciling FlyteWorkflow CRDs into pods |
| **Datacatalog** | Typed artifact metadata and lineage |
| **Blob storage** | S3/GCS/MinIO for serialized literals and checkpoints |
| **FlyteConsole** | UI for executions, inputs/outputs, and task logs |

Tasks are **strongly typed** Python (or other SDKs) with automatic caching of deterministic steps — strong fit for reproducible ML and data pipelines on K8s.

## Design principle

**Typed, cacheable workflows on K8s** — Propeller schedules pods; Admin holds metadata; compute stays in your cluster.
