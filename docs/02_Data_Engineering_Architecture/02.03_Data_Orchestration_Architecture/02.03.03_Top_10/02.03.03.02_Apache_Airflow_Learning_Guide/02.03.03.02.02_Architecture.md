# 2. Architecture of Apache Airflow

## Control plane vs execution plane

| Plane | Responsibility |
| --- | --- |
| **Control plane** | DAG parsing, scheduling, metadata, REST/UI |
| **Execution plane** | Task instances on workers or K8s pods |

## Core components

| Component | Function |
| --- | --- |
| **Scheduler** | Parses DAGs, creates DagRuns, queues task instances |
| **DAG processor** | Parses Python DAG files in isolated processes |
| **Webserver / UI** | Graph view, logs, admin, REST API |
| **Workers** | Pull tasks from queue (executor-dependent) |
| **Triggerer** | Runs deferrable operators without blocking worker slots |

Postgres or MySQL holds DAG definitions, run history, variables, connections, and XCom. Large XCom values belong in object storage with references only.

## Executor comparison

| Executor | Isolation | Scale pattern |
| --- | --- | --- |
| Local | Process on scheduler host | Dev |
| Celery | Worker pool | Fixed fleet |
| Kubernetes | Pod per task | Burst-heavy ELT |

## Design principle

Keep Airflow as **thin orchestrator, fat compute** — transforms run in Spark, warehouses, or containers.
