# 7. How to Configure Pub/Sub for Real-Time Scenarios

## Configuration matrix

| Goal | Publisher settings | Subscription settings | Consumer pattern |
| --- | --- | --- | --- |
| Low latency (< 100 ms) | Low `maxLatency` batching (5–20 ms) | Push to Cloud Run same region | HTTP handler, fast ack |
| High throughput | Large batches (`maxMessages` 100–1000) | Streaming pull | GKE/Dataflow workers |
| Strict ordering | `ordering_key` on publish | `enable_message_ordering=true` | Single-thread per key |
| No duplicates | — | `enable_exactly_once_delivery=true` | Idempotent sink still recommended |
| Resilience | Retry with backoff | Dead-letter topic, retry policy | DLQ processor sub |
| Cost efficiency | Batch to > 1 KB/request | Attribute filters | Fewer subs |

## Recipe 1 — Low-latency notifications (push)

**Target:** Order confirmation to email/SMS within 100 ms median.

```yaml
topic: notifications.orders.prod
subscription:
  type: push
  push_endpoint: https://notify.run.app/handle
  ack_deadline: 30
  min_retry_delay: 0
  max_retry_delay: 600
publisher:
  batch_max_latency_ms: 10
  batch_max_messages: 10
```

- Deploy Cloud Run in **same region** as topic usage.
- Set Cloud Run **min instances ≥ 1** for cold-start avoidance.
- Return HTTP 200 within ack deadline; offload SMTP to async task.

## Recipe 2 — High-throughput telemetry (streaming pull)

**Target:** 500k events/sec, 1 KB average.

```yaml
topic: iot.telemetry.prod
  message_retention_duration: 1d
subscription:
  type: pull
  ack_deadline: 60
publisher:
  batch_max_messages: 1000
  batch_max_bytes: 5242880
subscriber:
  flow_control_max_messages: 5000
  flow_control_max_bytes: 524288000
  use_streaming_pull: true
consumer: Dataflow or GKE (N parallel streaming pull clients)
```

- Request **quota increase** before load test.
- Shard across **multiple topics** if single-topic quota approached.

## Recipe 3 — CDC to lakehouse

**Target:** Near-real-time warehouse sync with replay.

```yaml
topic: cdc.customers.prod
  message_retention_duration: 7d
  schema_settings: { schema: customers-avro-v2 }
subscriptions:
  - name: cdc.customers.prod.bq
    bigquery_config: { table: project.ds.customers_changelog }
  - name: cdc.customers.prod.cache
    filter: 'attributes.op = "UPDATE" OR attributes.op = "INSERT"'
```

- Enable **topic retention** for replay after schema changes.
- Use **seek** to reprocess from timestamp after bug fix.

## Recipe 4 — Saga / workflow choreography

**Target:** Reliable multi-step business process.

```yaml
topics: [orders.created, payment.completed, shipment.requested]
subscriptions:
  - payment-service-sub (filter: eventType=OrderCreated)
  - shipping-service-sub (filter: eventType=PaymentCompleted)
dead_letter: orders.dlq.prod
retry_policy:
  minimum_backoff: 10s
  maximum_backoff: 600s
```

- Correlate with `saga_id` attribute.
- See [Saga Pattern](../../../02.01.02.04_Architecture_Patterns/02.01.02.04.03_Integration_Patterns/02.01.02.04.03.02_Saga_Pattern.md).

## Recipe 5 — Fraud scoring (sub-second)

**Target:** Score transactions in < 500 ms p99.

```
Card txn API → publish (ordering_key=account_id) → streaming pull scorer → alert topic
```

- **Ordering key** = `account_id` for sequence per account.
- In-memory state per worker + external feature store for cross-account rules.
- Scale horizontal with competing consumers **without** ordering if per-txn independence OK.

## Recipe 6 — Multi-tenant SaaS isolation

- Topic per tenant **or** shared topic with `tenant_id` attribute + filtered subscriptions.
- IAM conditions on `resource.name` prefix per tenant.
- CMEK per tenant for regulated industries.

## Recipe 7 — Replay after deployment bug

1. Stop buggy consumer (pause or remove subscription processing).
2. **Seek** subscription to `snapshot` or `timestamp`.
3. Deploy fixed consumer; enable exactly-once if not already.
4. Monitor DLQ during replay.

## Recipe 8 — Cross-region DR (warm standby)

- Primary publishers in `us-central1`.
- DR subscription in `us-east1` with acceptance of transfer cost.
- Failover: redirect consumers to DR sub; consider dual-publish for RPO ≈ 0.

## Monitoring thresholds

| Metric | Warning | Critical |
| --- | --- | --- |
| `oldest_unacked_message_age` | > 30 s | > 120 s |
| `num_undelivered_messages` | Sustained growth 15 min | > 1M backlog |
| Push `dead_letter_message_count` | > 0 sustained | > 100/hr |
| Publish error rate | > 0.1% | > 1% |
