# Data Product Mapping

## Purpose

Define how **data products** bind to **approved semantic concepts**, using the **[Entropy Data Product Marketplace](https://www.entropy-data.com/)** as product SoR and ODCS/ODPS `authoritativeDefinitions` plus the Mapping Engine as the link mechanism.

**Canonical contract (DA-10):** [Mapping Contracts](../01.%20Foundation/15.%20Mapping%20Contracts.md) § DA-10.

Demo: [Entropy marketplace](https://demo.entropy-data.com/demo772521358141/marketplace).

## Scope

| In scope | Out of scope |
| --- | --- |
| Binding schema, Entropy ODPS/ODCS links, soft/hard gates | Building a second marketplace UX in MCP |
| Central marketplace layering (Global / NATCO) | Separate marketplace deployments per NATCO |
| Reverse lookup (concept → products) | Physical pipeline SLAs |

## Platform decision

| Concern | System of record |
| --- | --- |
| **Data products**, marketplace UI, access, ports | **Entropy Data Product Marketplace** |
| Marketplace layering | **Global** + **NATCO-specific** layers (one central app) |
| **Enterprise meaning** | **Semantic Control Plane** (Registry / APIs) |
| Product ↔ concept links | **Mapping Engine** + ODPS/ODCS `authoritativeDefinitions` |
| Product specification | Prefer **ODPS**; DPS deprecated |
| Contracts | **ODCS** |
| Product-facing semantics UX | [Entropy Semantics](../02.%20Ontology/09.%20Entropy%20Semantics.md) (consumes control plane) |
| Federation | [Multi-NATCO Federation](../01.%20Foundation/07.%20Multi-NATCO%20Federation.md) |
| Interchange | **Apache OSSIE** (packages only) |

Architecture: [Architecture](../01.%20Foundation/05.%20Architecture.md).

### Marketplace layers

```text
Entropy Data Product Marketplace (central hosted)
 ├── Global layer     → Global products (owner: Global unit)
 └── NATCO layer(s)   → NATCO products (owner: each NATCO)
```

Product owners **maintain** products in this central app; layer scopes ownership, stewards, and discovery—not separate installs.

### Product classes

| Class | Marketplace layer | Owner | Semantic bindings |
| --- | --- | --- | --- |
| **Global product** | Global | Global unit | `global/*` only (TM Forum–aligned) |
| **NATCO product** | NATCO-specific | NATCO | **Required:** `global/*` when a global concept applies · **Optional:** `natco-*/*` for local freedom |

Cross-NATCO consumers resolve **`global/*` bindings first**; NATCO bindings are additive local context. Full policy: [Multi-NATCO Federation](../01.%20Foundation/07.%20Multi-NATCO%20Federation.md).

### NATCO dual-binding example

```yaml
# NATCO product — consistency via global + freedom via natco
authoritativeDefinitions:
  - type: "semantics"
    url: "https://…/semantics/global/Customer"          # required for shared meaning
  - type: "semantics"
    url: "https://…/semantics/natco-de/Kundenkonto"     # optional local enrichment
```

## Entropy product anatomy (adopt)

| Element | Role |
| --- | --- |
| **Data product** | Owned logical unit; statuses: proposed → in development → draft → active → deprecated → retired |
| **Output port** | Consumer endpoint (model + version + server + environment), usually backed by a data contract |
| **Input port** | Upstream products/apps consumed (declared or via access request) |
| **Data contract** | Schema, semantics, quality, terms of use for a port |
| **Marketplace** | Discovery / request / access for humans and AI; status can hide from marketplace |
| **AI context** (ODPS) | AI instructions, example questions/queries, exclude-from-AI |

Product types: source-aligned, aggregated, consumer-aligned (+ consumers / applications for landscape modeling).

## Definition (MCP binding)

A **data product mapping** declares which enterprise concepts and metrics a product (or its contract fields) **implements**, at a contract / product version.

In Entropy this is expressed as:

```yaml
authoritativeDefinitions:
  - type: "semantics"
    url: "https://…/semantics/{namespace}/{conceptId}"
```

Attachable at three levels:

1. Data product (ODPS) — whole product represents a concept  
2. Data contract / schema object — table/model represents a concept  
3. Field / property — column represents a concept  

## Schema (MCP crosswalk record)

| Field | Required | Description |
| --- | --- | --- |
| `mapping_id` | yes | Internal identifier |
| `source_id` | yes | Entropy data product ID (and optional output port / field path) |
| `contract_version` | yes | ODCS contract version (or product version) |
| `target_uri` | yes | Concept IRI / Entropy semantics URL |
| `mapping_type` | yes | `implements` \| `exposes` \| `measures` \| `authoritativeDefinition` |
| `link_level` | yes | `product` \| `contract` \| `field` |
| `natco_code` | yes | `global` \| NATCO code |
| `namespace` | yes | Entropy semantics namespace slug (`global`, `natco-de`, …) |
| `confidence` | yes | Steward-asserted vs suggested |
| `owner` | yes | Product owner |
| `status` | yes | `draft` \| `active` \| `deprecated` |
| `effective_from` | yes | Active-from timestamp |
| `version` | yes | Binding record version |

## Mandatory product binding rule

> A product is not “semantic” until its mapping to approved concepts is published.

| Maturity / mode | Gate behavior |
| --- | --- |
| Soft (until maturity level 4) | Warn if no `authoritativeDefinitions` of type `semantics` on product or ports; for **NATCO products**, warn if a matching `global/*` concept exists but is not linked |
| Hard (maturity level 4+) | Block marketplace certify / active publish without ≥1 approved concept link; **NATCO products** must link `global/*` when a global counterpart applies; metrics products require metric concepts |

## Reverse lookup (required)

From each concept (Entropy concept page / Semantic API): list all data products and contracts that reference it. Enables “which products implement Customer?” and “who owns MRR?”.

## Consistency with technical mappings

- Product links to concept C at product or contract level  
- At least one field under its contracts should `represents` C or a property of C (soft in v1)

## Lifecycle

1. Product owner proposes links in Entropy (Studio) or via ODPS/ODCS YAML  
2. Steward confirms concept status `approved` in the target namespace  
3. Binding active with contract version; audited in Entropy  
4. On concept deprecation: warn (soft) / block next certify (hard)  
5. Emit `product.binding.changed` for MCP consumers / Ossie rebuilds  

## System of record

- **Products / marketplace / contracts:** Entropy Data Product Marketplace  
- **Concepts:** Semantic Control Plane  
- **Crosswalk / gates:** Mapping Engine + Control Plane status  
- **Interchange packages:** Apache OSSIE (exchange only)
