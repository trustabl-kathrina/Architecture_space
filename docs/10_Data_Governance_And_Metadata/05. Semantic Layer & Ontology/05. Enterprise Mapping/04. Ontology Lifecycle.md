# Ontology Lifecycle

## Purpose

Define how **Semantic Control Plane** ontology slices and **Apache Ossie** packages are versioned, released, deprecated, and consumed so Marketplace, catalogs, and APIs stay consistent.

**Concept/edge approval (DA-12):** [Governance Engine](../01.%20Foundation/17.%20Governance%20Engine.md).  
**Package contents / SemVer (DA-14):** [Ossie Package Contract](../01.%20Foundation/19.%20Ossie%20Package%20Contract.md).  
Governance Engine owns approval; Ossie owns interchange packages only.

## Scope

| In scope | Out of scope |
| --- | --- |
| Versioning, release, deprecation, replace-with, notifications | CI tooling vendor choice |
| Compatibility rules for mappings and products | Full OWL reasoning regression suites (v1) |

## Lifecycle states

```text
build → release_candidate → released → superseded
                 ↘ rejected
concept/status path: draft → review → approved → deprecated
```

## Versioning

| Level | Scheme | Notes |
| --- | --- | --- |
| Ossie model slice | SemVer `MAJOR.MINOR.PATCH` | Per domain package + enterprise shared |
| Individual element | Monotonic `version` integer + `effective_from` | Stable ID / URI never changes |

**Compatibility**

- **MINOR/PATCH** — additive labels, new optional fields, documentation
- **MAJOR** — removed elements, changed grain/meaning of an approved metric or entity (prefer deprecate + `replaced_by` instead of silent redefine)

## Deprecation policy

1. Set element `status=deprecated` and set `replaced_by` when a successor exists
2. Keep ID/URI resolvable indefinitely (or per enterprise retention policy)
3. Block **new** Business / Technical / Product mappings to deprecated IDs
4. Existing product bindings: warn on soft gate; require migration plan before next **MAJOR** contract bump on hard gate
5. Emit change event (see [APIs](../07.%20Engineering/01.%20APIs.md) / events)

## Release process

1. Inventory subset marked `approved`
2. Build produces **Ossie** YAML/JSON model packages
3. **Ossie schema validation** gate passes (project validation tooling)
4. Release candidate reviewed by Domain Steward + Architecture COE (enterprise shared)
5. Publish version tag + release notes
6. Semantic API serves new version; previous `released` becomes `superseded` but remains readable by version pin
7. Optional: run converters to refresh BI / dbt projections

## Mapping and product impact

| Event | Required action |
| --- | --- |
| Concept / metric approved | Eligible as mapping target |
| Concept / metric deprecated | Notify owners of dependent crosswalks and products |
| MAJOR Ossie release | Product owners review bindings within SLA |
