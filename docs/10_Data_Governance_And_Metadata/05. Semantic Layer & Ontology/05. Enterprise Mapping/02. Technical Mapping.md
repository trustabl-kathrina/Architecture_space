# Technical Mapping

## Purpose

Define the crosswalk from **Technical Catalog** assets to concept IRIs. NATCOs use **either Collibra or Dataplex**—same mapping schema, different `source_system`.

**Canonical contract (DA-09):** [Mapping Contracts](../01.%20Foundation/15.%20Mapping%20Contracts.md) § DA-09.

## Scope

| In scope | Out of scope |
| --- | --- |
| Collibra and Dataplex asset → concept mappings | Replacing lineage engines |
| Per-NATCO connector configuration | Forcing all NATCOs onto one catalog vendor in v1 |

## Platform decision

| NATCO pattern | Technical catalog SoR |
| --- | --- |
| Pattern A | **Collibra** (technical assets) |
| Pattern B | **Google Dataplex** |

Both feed the **Semantic Control Plane** via the Mapping Engine (`represents` → `global` or `natco-*` concepts). See [Architecture](../01.%20Foundation/05.%20Architecture.md) · [Multi-NATCO Federation](../01.%20Foundation/07.%20Multi-NATCO%20Federation.md).

## Definition

A **technical mapping** annotates a technical asset (or field) with semantic meaning. Preferred predicate: `represents`.

## Schema

| Field | Required | Description |
| --- | --- | --- |
| `mapping_id` | yes | Internal identifier |
| `source_id` | yes | Catalog asset / field ID |
| `source_system` | yes | `collibra` \| `dataplex` |
| `source_type` | yes | `dataset` \| `table` \| `column` \| `api_field` \| `pipeline` \| `topic` \| `other` |
| `natco_code` | yes | Owning NATCO |
| `target_uri` | yes | Concept or property IRI |
| `target_namespace` | yes | `global` \| `natco-{code}` |
| `mapping_type` | yes | `implements` \| `represents` \| `documents` \| `suggested` |
| `confidence` | yes | Steward-asserted vs machine-suggested |
| `owner` | yes | Technical owner or steward |
| `status` | yes | `draft` \| `active` \| `deprecated` |
| `effective_from` | yes | Active-from timestamp |
| `version` | yes | Mapping version |
| `grain_note` | no | e.g. surrogate key for entity |

## Grain guidance

| Asset | Typical target |
| --- | --- |
| Table / dataset | Entity IRI (prefer `global` when comparable) |
| Column / API field | Shared property / inline property IRI |
| Pipeline | Optional `documents` link |

Prefer column-level mappings for AI grounding.

## Rules

1. Prefer mapping to **global** concepts when the asset implements shared meaning; use NATCO concepts for local-only fields.  
2. `target_uri` must be `approved` for active `implements` / `represents`.  
3. Machine suggestions (`suggested`) require steward promotion.  
4. Technical mappings do **not** replace lineage.  
5. On concept deprecation, remap within SLA.

## Connector notes

| System | Identity tips |
| --- | --- |
| Collibra | Use stable Collibra asset GUID / qualified name in `source_id` |
| Dataplex | Use entry name / fully qualified Dataplex resource ID in `source_id` |

## System of record

- **Asset inventory:** Collibra or Dataplex (per NATCO)  
- **Meaning URIs:** Semantic Control Plane  
- **This crosswalk:** Mapping Engine
