# Semantic Relationships

## Purpose

Define the **controlled vocabulary of typed edges** for the Semantic Control Plane (Mapping, Federation, Ontology, Knowledge Graph)—inspired by [OpenMetadata](https://github.com/open-metadata/OpenMetadata)’s relationship style.

**Canonical predicate list (DA-07):** [Predicate Catalog](../01.%20Foundation/14.%20Predicate%20Catalog.md).  
**Pilot ontology structure (DA-06):** [Ontology and Taxonomy](../01.%20Foundation/13.%20Ontology%20and%20Taxonomy.md).

Business meaning edges (e.g. `Customer owns Account`) and catalog context edges (e.g. `Column represents Customer Identifier`) share the same relationship-object pattern.

## Scope

| In scope | Out of scope |
| --- | --- |
| Relationship types, endpoints, cardinality, governance | Graph DB product selection |
| Enterprise relationship catalog (v1 core + extensions) | Entity resolution algorithms (03. Entity Resolution — deferred) |
| Publication into Ossie / Semantic API | Replacing physical lineage engines |

## Definition

A **relationship** is a governed, directed, typed association between two entities in the [Context Model](07.%20Context%20Model.md), with owner, status, and stable ID.

## Maintainable attributes

| Attribute | Required | Description |
| --- | --- | --- |
| `relationship_id` | yes | Internal MCP identifier |
| `uri` | yes | Stable relationship-type or instance IRI |
| `predicate` | yes | Controlled edge name (`hasColumn`, `represents`, …) |
| `source_id` / `source_kind` | yes | From entity |
| `target_id` / `target_kind` | yes | To entity |
| `cardinality` | yes | e.g. `1:1`, `1:N`, `N:M` |
| `inverse_predicate` | no | Inverse edge if modeled |
| `owner` / `steward` | yes | Accountable roles |
| `status` | yes | `draft` \| `review` \| `approved` \| `deprecated` |
| `confidence` | no | For suggested / inferred edges |
| `version` | yes | Publication version |
| `effective_from` | yes | Active-from timestamp |

## Relationship catalog (v1 core)

### Structure and inventory

```text
Table               ──hasColumn────────────> Column
Dashboard           ──dependsOn───────────> Table
Pipeline            ──produces────────────> Table
Column              ──flowsTo─────────────> Column
```

| Predicate | From → To | Meaning |
| --- | --- | --- |
| `hasColumn` | Table → Column | Structural containment |
| `dependsOn` | Dashboard → Table (or Metric) | Consumption dependency |
| `produces` | Pipeline → Table / Topic | Pipeline output |
| `flowsTo` | Column → Column | Column-level lineage hop |

### Semantics (meaning) — Entropy + multi-NATCO

```text
Entity              ──hasProperty──────────> Shared Property / Property
Entity              ──isA──────────────────> Entity
Concept             ──memberOf─────────────> Group
Metric              ──measures─────────────> Entity / Property
Metric              ──derived_from─────────> Metric / Concept
NATCO Concept       ──sameAs|specializes───> Global Concept
NATCO Concept       ──implements|extends───> Global Concept
Column / Field      ──represents───────────> Concept (authoritativeDefinitions)
Metric              ──definedBy───────────> Concept
Column              ──classifiedAs─────────> Classification (e.g. PII)
```

| Predicate | From → To | Meaning |
| --- | --- | --- |
| `hasProperty` | Entity → Property | Entropy entity composition |
| `isA` | Entity → Entity | Specialization |
| `memberOf` | Concept → Group | Subject-area membership |
| `measures` | Metric → Entity / Property | Metric scope |
| `derived_from` | Metric → Metric / Concept | Formula dependency |
| `sameAs` | NATCO → global | Same meaning |
| `specializes` | NATCO → global | Stricter subtype |
| `implements` | NATCO → global | Local operationalization |
| `extends` | NATCO → global | Adds NATCO-only attributes |
| `classifiedAs` | Asset → Classification | Sensitivity or category |
| `represents` | Column / Field → Concept | ODCS / catalog field → semantics |
| `definedBy` | Metric → Concept | Metric meaning anchor |

See [Multi-NATCO Federation](../01.%20Foundation/07.%20Multi-NATCO%20Federation.md).


### Ownership and products

```text
Table               ──ownedBy─────────────> Team / User
Table               ──partOf──────────────> DataProduct
DataContract        ──appliesTo───────────> Table / DataProduct
```

| Predicate | From → To | Meaning |
| --- | --- | --- |
| `ownedBy` | Asset → Team / User | Accountability |
| `partOf` | Asset → DataProduct | Product composition |
| `appliesTo` | DataContract → Asset / Product | Contract scope |

Product–concept binding remains mandatory for “semantic” products: [Data Product Mapping](../05.%20Enterprise%20Mapping/03.%20Data%20Product%20Mapping.md).

### Quality and governance

```text
TestCase            ──validates───────────> Table / Column
Policy              ──governs─────────────> Classification / Asset / Domain
```

| Predicate | From → To | Meaning |
| --- | --- | --- |
| `validates` | TestCase → Asset | Quality evidence |
| `governs` | Policy → Classification / Asset | Policy scope |

### Lineage events

```text
OpenLineageEvent    ──updatesLineageFor───> Pipeline
```

| Predicate | From → To | Meaning |
| --- | --- | --- |
| `updatesLineageFor` | OpenLineageEvent → Pipeline | Event that refreshes lineage |

Physical lineage detail lives in Lineage capability; this edge types the event attachment.

### Memory and AI tribal knowledge

```text
AgentConversation   ──capturedAs──────────> Memory
Memory              ──informs─────────────> DataProduct
Memory              ──documentsDecisionFor> Metric / Concept
Memory              ──attachedTo──────────> Table / Column / Topic / Dashboard / Pipeline / API
```

| Predicate | From → To | Meaning |
| --- | --- | --- |
| `capturedAs` | AgentConversation → Memory | Persist thread outcome |
| `informs` | Memory → DataProduct | Product context from learnings |
| `documentsDecisionFor` | Memory → Metric / Concept | Decision rationale |
| `attachedTo` | Memory → Asset | Anchor memory on catalog entities |

Memory edges are P2/P3 after core semantic and technical edges exist in the pilot.

## Relationship categories (summary)

| Category | Core predicates |
| --- | --- |
| Structural | `hasColumn`, `partOf` |
| Semantic | `represents`, `definedBy`, `classifiedAs` |
| Ownership | `ownedBy` |
| Dependency / lineage | `dependsOn`, `produces`, `flowsTo`, `updatesLineageFor` |
| Quality / governance | `validates`, `governs`, `appliesTo` |
| Memory | `capturedAs`, `informs`, `documentsDecisionFor`, `attachedTo` |
| Business meaning (domain) | `owns`, `consists_of`, `derived_from`, … (domain-approved) |

Prefer this controlled set; domains add predicates only with Architecture COE review.

## Governance statuses

Only `approved` relationships are returned as certified by default Semantic API filters and are eligible for hard product gates.

## Mapping to Ossie and APIs

| Consumer | Use |
| --- | --- |
| Ossie publication | Semantic predicates (`represents`, `definedBy`, domain business edges) |
| Technical Catalog | Structural and ownership edges on assets |
| Lineage | `flowsTo`, `produces`, `updatesLineageFor` |
| Semantic API `expand` | Walk approved predicates from a node |
| Data products | `partOf`, `appliesTo`, plus concept bindings |

## Pilot minimum (v1)

Implement and query these first:

1. `hasColumn`
2. `represents`
3. `ownedBy`
4. `partOf`
5. `definedBy`
6. `produces`
7. `flowsTo`
